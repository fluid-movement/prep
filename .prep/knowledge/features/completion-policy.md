A project explicitly records how work is verified and how documentation impact is reviewed with `prep policy set --verification <method> --documentation <method>`. `prep policy show` reports those methods, attribution and configured state; JSON also includes the existing project Definition of Done. prep records the contract and never executes check commands.

The policy is stored as `completion_policy` in project.md frontmatter, with verification, documentation, by and at fields. Attribution is not authenticated human approval. Existing project DoD bullets continue to cascade; they do not count as an explicit completion policy. Missing policy blocks new ready transitions with G_POLICY, but does not block capture or definition. Legacy ready and resolved records are not rewritten or assigned fabricated evidence. A malformed configured policy is P010.

New ready records snapshot a completion contract: verification and documentation methods, effective DoD items and opt-outs, acceptance criterion text, and ancestor IDs. Requirement IDs and the contract ID are deterministic content hashes. Criterion checkboxes, policy attribution/time, UI configuration, and Git commit identity do not change contract identity. Changed methods, effective requirements, or ancestry invalidate the binding. Claim and completion then require explicit reconciliation; policy changes do not rewrite historical resolutions. Changed project methods archive earlier policies in completion_policy_history; adoption archives earlier bindings in ready.previous_contracts. `prep policy show <id>` compares the bound and current contract; `prep policy adopt <id>` explicitly adopts the current one without changing the requirement baseline or claiming work. Claimable-work queries exclude issues needing policy reconciliation; explicit human approval may retain the older bound policy for the reviewed change. I029 warns about changed bindings; inconsistent stored contract hashes are I015 errors.

Per-requirement verification is recorded with `prep evidence record <id> --requirement <hash> --result pass|fail --method manual|automated --observation <text> --scope <path>`; scope is repeatable and project-relative. Automated reports require the command already run by the agent; prep never executes it. `--config-scope` binds check configuration and `--source` stores an optional report reference. Every report is explicitly agent-reported, not independently authenticated. `prep evidence show <id>` reports current applicability and reasons for changed work, configuration or contract. The guide offers these commands when an issue has a bound contract.

Reports in verification.md include contract and requirement identity, actor/time, observation, command/source, scopes, SHA-256 content fingerprint, and a content-hash history chain. The latest report for each bound requirement controls completion: missing, failed or inapplicable reports block it with G_EVIDENCE. A previous pass cannot mask a later failure. Resolutions snapshot the bound contract and selected reports. Unchanged scoped content permits reuse; changed work or check configuration invalidates affected reports. Reporting reads do not rewrite records.

`internal/worktree` computes fingerprints of explicitly scoped paths without requiring Git or a commit. It includes file names, modes, contents, untracked files and missing paths. Git metadata and prep bookkeeping are excluded; knowledge content is included. Absolute paths, paths outside the project, bookkeeping scopes and symlinks are rejected. Scope coverage and observations are agent reports, not proof that every affected path or required check was identified correctly.

Human approval now covers scoped verification exceptions, retaining an older policy after reviewing a new one, and inherited DoD opt-outs. These are explicit human-attributed actions with reasons, recorded as versioned approvals; declaring a human actor on another record does not create approval. Work/check changes or a new failure invalidate an exception; further policy changes require renewed retention approval. Completion snapshots the approvals used and the actual bound DoD. See [Completion approvals](/features/completion-approvals.md) for commands, applicability and the local trust model.

Completion approval/reopening and TUI review belong to subsequent children. Legacy ready records have no bound contract until explicitly adopted; legacy resolutions remain readable without fabricated verification or approvals. A contract or --docs reference alone does not prove documentation was reviewed or updated; enforce that in 01M4WSRP2FYKRNT2P61T88X9TH.
