`prep brief <id>` prints a text that an agent with no knowledge of prep can work from. For an implementer it holds, in this order: one line on what the agent is asked to do, the requirement, the implementation context, the acceptance criteria (numbered), the decisions that apply with their description and body, the Definition of Done, the rules of the role (implement exactly this, run the checks the context lists, never commit or push, stop and report a conflict instead of bending tests, do not read or change `.prep`), and the report format to return. `prep brief <id> --check` is the checker's version: the same issue content, the checker's rules (verify each criterion yourself, run the checks, read the change from the worktree or diff), and the checker's report format.

The text contains no prep commands and no record paths. `--out <file>` writes it to a file and prints only the path, so an orchestrator can hand it over without the text entering its own context.

The decisions that apply are those linked to the issue or to one of its ancestors, and current decisions whose scope matches a path the context names in backticks. Superseded decisions are left out. Each is bounded in length; when the bound cuts one, the brief says so.

A brief is given only for a code or research issue that is ready or in progress, not stale, with dependencies done; otherwise the command fails and names what is missing. For a research issue the report asks for findings instead of a criteria verdict.

Why: decision 01M72AV3FRS077RJ3DPXZFX23M (hand-off by brief). The orchestrator wrote every hand-off by hand in the daypack sessions, and implementers need a prep installation today only to read their issue and report back.

The report format is defined once and shared with `prep handback` (sibling issue): Markdown with the headings `## Summary`, `## Criteria` (one line per number: met or not met, with the evidence), `## Decisions` (each a title line and a reason), `## Findings`, `## Problems`. Empty sections may be left out.
