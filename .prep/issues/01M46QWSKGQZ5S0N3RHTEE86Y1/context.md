Today the look is one fixed palette in `internal/tui/theme/theme.go` (see [TUI design system](/components/tui-design-system.md)): nine semantic tokens plus one color per state and kind, each with true-color, 256 and 16-color values for dark and light. `theme.New(dark, profile)` resolves them; programs rebuild `*th` in place on `tea.BackgroundColorMsg`/`tea.ColorProfileMsg` (`internal/tui/tui.go` gallery, `app.go` `NewModel` and line ~200, `checklist.go`). `Theme.Hex` feeds Glamour in `ui/markdown.go`. `Theme.Tokens` feeds the gallery's color section.

Plan:

- **Palette package** `internal/palette` (no TUI dependencies, so mdstore and the CLI can validate and print themes): token names (`text`, `muted`, `subtle`, `accent`, `border`, `selection`, `success`, `warning`, `error`, `state.open` … `state.dropped`, `kind.code` … `kind.decision`), the built-in themes, and `Resolve(name, custom)` that walks `base:` chains and returns a full palette for dark and light, with errors for unknown tokens, invalid colors, unknown bases and cycles.
- **Built-ins**: `default` (today's values, including the hand-picked 256/16 fallbacks, so existing goldens stay unchanged), `high-contrast`, `monochrome`, `pastel`, `catppuccin` (Mocha dark, Latte light), `nord` (Polar Night dark, Snow Storm light), `gruvbox` (dark and light). Every built-in defines every token for both backgrounds. Non-default built-ins and custom themes give true-color hex only; 256 and 16 colors come from Lip Gloss downsampling for the detected profile.
- **Theme package**: `theme.New(p palette.Palette, dark, profile)`; `Theme` keeps its palette and name so the background/profile rebuilds keep the chosen theme. `State`, `Kind`, `Hex`, `Tokens` read the palette. NO_COLOR and the ASCII profile behave as today (the profile drops colors).
- **Config** (`internal/mdstore/store.go` `configFile`, `domain.Config`): `theme: <name>` (default `default`) and `themes: {<name>: {base: <name>, dark: {token: "#hex"}, light: {token: "#hex"}}}`. `loadConfigFile` validates through `palette.Resolve`, so `prep check` reports problems as P003 with the file name. `renderConfig` must write `theme` and `themes` back (in file order, like views), otherwise a settings save would drop custom themes. `domain.PlanConfig` gets the same validation through a function the store passes in, or palette moves under domain's reach; domain must not import TUI packages.
- **Gallery** (`internal/tui/tui.go` `RunGallery`, `ui.Gallery`): `prep tui --gallery` loads the project's config when run in a prep project (custom themes and the selected theme) and works without one (built-ins only). `t` switches to the next theme, `T` to the previous; the header names the theme; every component re-renders. The color section shows state and kind tokens too.
- **Settings screen** (`internal/tui/app.go` `settingsPane`, `editing.go` `settingsKey`): a Theme row before the views; space or enter cycles through the themes, re-rendering the whole TUI right away, and saves `theme:` to the user's own `.prep/config.yaml` through `PlanConfig` (created from config.yaml.dist on first save, see 01M4AHPY6HZ0ZFMMH349V1V2TC). Row indexes for views and digits shift by one.
- **CLI** (`internal/cli`): `prep theme list` prints built-in and custom themes, marking the active one; `prep theme new <name> [--from <theme>]` resolves `--from` (default: the active theme) and writes `themes.<name>` with every token for dark and light into `.prep/config.yaml`, then selects it. It refuses an existing name and built-in names. Writes go through `PlanConfig` and the store like the settings screen.
- **Docs/knowledge**: README (themes section), tui-design-system, tui-editing, storage-format, markdown-store, cli; a new component entry for the palette package.
