Builds on the TUI ([TUI](/components/tui.md), [TUI design system](/components/tui-design-system.md)) and the write pipeline ([Domain](/components/domain.md), [Markdown store](/components/markdown-store.md), [CLI](/components/cli.md)).

- Overlay: `ui.Overlay(t, background, block, width, height)` in `internal/tui/ui/modal.go` composites a dialog over the screen: the background lines are stripped of styling and drawn in the subtle tone (dimmed), and the block's lines are spliced in centered with the ANSI-aware `ansi.Cut`/`ansi.Truncate` from `charmbracelet/x/ansi` (already a dependency). `Model.View` (`app.go`) renders the normal body first and, with a modal open, overlays `modalView` on it instead of replacing it; `ui.Center` stays for empty states.
- Multi-line editing: Bubbles `textarea` (in `bubbles` v1.0.0) in a new `ui.TextArea` wrapper styled with the design system (static cursor, no blink, as the text inputs). The create dialog (`openCreate` in `actions.go`) gains the requirement field after title and kind; `PlanNew` already takes `Body`. A new `modalText` dialog edits requirement or context inline: ctrl+s saves through `PlanEdit` (requirement) or `PlanRecord` with `OpContext`, esc cancels, ctrl+e writes the current text to a temp file and runs the existing `runEditor` hook, loading the result back into the field. The rejected-text memory (`drafts` per issue and field) keeps working for both paths. `e` and the new `E` open this dialog instead of going straight to `$EDITOR`.
- Direct keys (decision D2): `E` context, `k` criteria, `i` priority, `>` next transition, from list and detail; `keyHelp` and the footer list them. `>` picks the issue's next transition as `prep guide` ranks them (ack when stale; else the first forward transition; complete and drop open their dialogs); input-free ones need a second `>` within the footer prompt. A key that does not apply flashes the gate's reason via `flashErr`.
- Action menu: `actions()` drops entries with a `reason` instead of listing them; `TestActionMenu` changes accordingly.
- Settings: `domain.PlanConfig(cfg Config)` returns a `Change{Op: "config", Config: &cfg}`; `CheckWrite` validates commit mode and every view query with `ParseFilter`, and `Tree.Apply` swaps the project config. `mdstore` renders config.yaml with the existing header comment, `commit_mode`, and `views` in `ViewOrder` (a `yaml.Node` mapping keeps order), and `Apply` writes it. The settings screen (`settingsPane`, `screenSettings`) becomes a selectable list: commit mode (space toggles), the views (enter edits name and query in a two-field dialog, `n` adds, `d` deletes after confirmation, shift+up/down reorders), the project DoD stays read-only. The write goes through `Options.Write`; the commit message names `config`. After the reload the tabs are rebuilt from the new `ViewOrder`.
- Tests: `ui.Overlay` unit test; screen snapshots with a dialog over the dimmed screen at 110×28 and 80×24; create with requirement; inline edit, ctrl+e round trip via the `runEditor` hook, rejected text kept; direct keys and the `>` confirmation; menu without unavailable entries; settings: toggle commit mode, add, rename, reorder, delete a view, invalid query rejected; mdstore config round trip (order and header kept); domain `PlanConfig` validation.
