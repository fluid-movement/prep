Options, with the evidence for each.

(a) Stay out of prep unless the user names an issue or asks for tracking. Cheapest; keeps prep invisible for small fixes. Cost: the tracker silently drifts from reality (an issue "Profile headline gets cut off" stays open and ready while the fix lands), and the knowledge entries that describe the changed code go stale.
(b) If a tracked issue clearly covers the request, claim it, log progress and complete it with its knowledge and criteria (the skill's full loop); otherwise just do the work and create nothing. This is what the suite's natural cases currently assume. Evidence that it is achievable: sonnet did exactly this on `natural-fix-matching-issue` (found the issue, claimed it, changed `db/schema.sql` and `src/lib/profile.ts`, confirmed the knowledge entry, completed); on `natural-fix-no-issue` (a fix with no issue) sonnet and haiku fixed the code and created nothing. Haiku did NOT do it: it fixed the code and never looked at the tracker (0/3).
(c) Always track substantial work, filing an issue first when none exists. Strongest record; most overhead; risks noise (many small issues) and agents filing issues the user did not want. The real sessions in the other prep projects (fpa-api, fpa-events, fpa-profiles, fathom) show users asking explicitly for issues when they want them ("lets create an issue to add pagination", "i have an issue to file"), which suggests users expect to be in control of what is filed.

What the decision changes: the assertions of `eval/cases/natural/*.yaml` and `real/*.yaml`; the wording of the skill (`internal/cli/skill.md`, copied to `plugins/claude-code/skills/prep/SKILL.md` and `.claude/skills/prep/SKILL.md` by `just sync-skill`); whether the hook should nudge at all (see the fix issue 01M4QY30FKG3RNFSREWCZCPF9W); the hooks issue 01M4J8789E81QAJHG8R8ZPEMRD ("hooks make sure prep calls are made") which currently has no definition of "a call that should have been made".

Recommendation from the evidence: (b), with the nudge made by the plugin rather than by more skill text, and explicit user requests for issues always honored. Record the decision with `prep decide <id> --title ... --outcome`.
