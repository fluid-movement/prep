- `internal/setup`: the `Harness` interface (`Name`, `Detect` whether the harness is on the machine, `Installed` version or none, `Install(version)` which also updates, `Remove`) and a registry. Claude Code's implementation comes with the plugin issue; this issue ships the interface, the registry, a fake harness for tests, and the flow around them.
- `internal/userconfig`: `$XDG_CONFIG_HOME/prep/config.yaml`, default `~/.config/prep/config.yaml`, holding `harnesses: [claude-code]`; strict YAML decode, atomic write, created on first save. Only choices: what is installed is asked from each harness (design principle 3, [Design principles](/decisions/design-principles.md)). It is also the future home of the TUI theme choice (20261005-191550).
- `prep setup` (`internal/cli/setup.go`): interactive selection as a small Bubble Tea checklist built from the [TUI design system](/components/tui-design-system.md), reading keys from the terminal (`/dev/tty`, `CONIN$` on Windows) so it works under `curl | sh`; `--harness a,b` installs exactly those, `--remove name` removes one, `--refresh` brings configured harnesses to the binary's version, all with `--json`. It writes outside the repository, so it is a write command for the harness's permission rules ([CLI](/components/cli.md)).
- `install.sh`: after installing, runs `prep setup` with stdin from `/dev/tty` when one is available, else prints the command ([Release, install and update](/components/release.md)).
- `prep update`: after replacing the binary, runs the new binary's `prep setup --refresh`, so the refresh uses the new version's code and harness list.
- Tests: a fake harness records calls; `XDG_CONFIG_HOME` points at a temp dir; the checklist model is driven like the TUI tests.
- Docs at completion: a new entry `components/setup.md`; [Out of scope](/decisions/out-of-scope.md) loses "user-level config: project-level only"; CLI and release entries.
