Decide whether prep moves to two roles. The orchestrator is the only agent that knows prep. To hand an issue off it gets a brief from the binary (working name `prep brief <id>`): one self-contained text with the requirement, implementation context, acceptance criteria, the content of the decisions that apply (linked to the issue or scoped to the files the context names), the Definition of Done, the checks to run and the format of the report to return. The brief contains no prep commands. The implementer, in any harness, does the work and returns the report. The orchestrator hands the report back in one command (working name `prep handback <id> --report <file>`) that writes the work log, any decisions and findings the report names, and for a checker's report the checked criteria and the completion.

Why consider it:

- Implementers stay light. They need no prep binary, plugin, skill or hooks, which matters for Pi and for sandboxes; any harness that can read a file can implement a prep issue.
- The hand-off is written by hand today. In the daypack sessions the orchestrator wrote 39 subagent prompts (about 1,400 characters each) and prompt files for 68 `codex exec` runs, each restating the prep protocol, and told implementers to run both guide and show.
- Implementers spend on bookkeeping. Subagents averaged 4 prep calls each (guide 38, check 22, log 21, complete 16, show 15, knowledge find and show 17), and requests that only ran prep were 9.3% of subagent cost (finding 01M72A9TBJ5JQXT2VGT15N2HW1).
- Records get one writer. Implementers writing records in their own worktrees produce merge conflicts in the knowledge indexes (seen in fpa-events), and claims and activity are local to a worktree.
- The brief is where "ready means another agent without this conversation could do the work" becomes checkable: if the brief is not enough, the issue was not ready.

What it costs:

- Bookkeeping moves from a small, cheap implementer context to the orchestrator's large one. It stays cheap only if hand-back is one command fed from a file, so the report's content is not rewritten by the orchestrator.
- The brief must not pass through the orchestrator's context as output: it is written to a file or piped to the implementer's command line, and the subagent prompt is one line pointing at it.
- An implementer can no longer look up knowledge mid-work; the brief has to carry it. That depends on decisions being linked or scoped (see the sibling issue on unscoped decisions).
- A session working alone is both roles and keeps today's flow; guide stays for it.
