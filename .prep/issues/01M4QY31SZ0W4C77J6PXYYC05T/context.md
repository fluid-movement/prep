Evidence. Case `eval/cases/real/bug-to-issue.yaml`, fixture `eval/fixtures/webapp.yaml` (open issue "Profile badge needs a hard refresh", no parent link to the new text). Prompt (in the style of real users, from the fpa-profiles project): "i have an issue to file. i added some data to a player in the app, saved, went back to the list and had to hard refresh for the profile badge to show up. the bigger problem was that when i cleared that data again, the badge stayed until i refreshed twice." Good behavior seen once on sonnet: `prep list --text badge`, `prep show`, `prep edit` with a body that adds the clearing symptom; its final message said it did not file a new issue because one existed. Bad behavior: `prep new --help; prep flags; prep new ...` then done, and in one haiku run the final message said "I didn't look for related issues, so I don't know whether this duplicates an existing one" (honest, but the duplicate exists).

Options. (1) `prep new` prints, after creating the issue, up to three similar open issues ("similar open issues: <id> <title>") found by title words and text (`domain.Filter{Text: ...}` and `Tree.Query` already do the matching that `prep list --text` uses; see `cmdNew` in `internal/cli/write.go`); the agent reads the output of the command it just ran, so it works for any model. Cheap, deterministic, testable in Go. (2) The same check before creating, refusing unless `--allow-duplicate`: stronger but blocks legitimate near-duplicates and surprises scripts; not recommended. (3) Skill text "search before filing": costs tokens for every session; sonnet follows it half the time, haiku not at all in this case.

Implementation notes for (1): choose words from the title (drop stop words, lower-case), match against titles and requirements of unresolved issues, rank by overlap, skip the new issue itself, cap at three, print only when there is a match; add the same list to the JSON result (`similar`). Tests in `internal/cli/cli_test.go` (create two issues with overlapping titles; assert the hint; assert silence when unrelated). The skill and [CLI](/components/cli.md) mention the hint; the agent-facing wording should say what to do ("extend it with prep edit, or link it, if it is the same problem").

Verify with the suite: `prep eval run --case real-bug-report-to-issue --models haiku,sonnet --n 5`. The case's rubric asks for no duplicate; the deterministic part only checks that the agent looked (`any_of list/show/next`) - after the change a haiku run that creates first and then reads the hint and edits instead should pass the rubric.
