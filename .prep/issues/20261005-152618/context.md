First writes from the [TUI](/components/tui.md). The domain stays the only place with rules ([Domain package](/components/domain.md)); the TUI plans changes with the same functions as the CLI's write commands ([CLI](/components/cli.md)): `Tree.PlanNew`, `Tree.PlanEdit` (title, parent, requirement), `Tree.PlanRecord` (context, criteria), `Tree.Plan` (define, ready, ack, drop, complete).

- Writing: `Options` gets `Write func(plan func(*domain.Tree) (*domain.Change, error)) (string, error)` and `Actor string`. The CLI implements Write like its own pipeline: fresh stores, load, plan, `CheckWrite`, `store.Apply`, then stage or commit per commit mode. Staging is factored out of `afterWrite` (`internal/cli/cli.go`) so the TUI path returns git problems instead of printing to stderr under the alternate screen. Writes are serialized with a mutex. The actor is `human:` plus the OS user name, so the existing `G_ACTOR` gate keeps code completion with agents.
- Action menu (`a`): items for new issue, title, requirement, context, criteria, reparent, define, ready, acknowledge, drop and complete, each with a key. Transitions are enabled or explained with `Tree.Gates` evaluated with the human actor and placeholder arguments (reason, no-impact), so only state and content gates show; edits are disabled on resolved issues. Global shortcuts: `n` new issue, `e` edit requirement.
- $EDITOR: `tea.ExecProcess` suspends the TUI and runs `$VISUAL`, `$EDITOR` or `vi` on a temp `.md` file. When it closes the text is planned and validated; on rejection the error stays visible and the text is kept per issue and field for the next `e`. Unchanged text writes nothing. Tests replace the editor runner.
- Modals: new design system components (`ui.Modal`, `ui.MenuRow`) rendered centered over the body; forms use Bubbles text inputs styled from the theme. A modal stays open with the error when its write is rejected and closes on success.
- After a write the TUI reloads (the watcher would too) and keeps or moves the selection to the changed or created issue.
- Tests in `internal/tui/app_test.go` use a Write that runs the same pipeline on the fixture: create, rename, requirement and context through the editor hook, criteria, reparent, define, ready, ack, drop, complete of a manual issue, refusal for a code issue, rejected edits keeping the text.
